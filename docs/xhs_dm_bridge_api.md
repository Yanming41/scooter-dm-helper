# 小红书私信传输层 API 文档

脚本：`~/IdeaProjects/scooter-dm-helper/xhs_dm_bridge.mjs`

**这个脚本只做私信收发的传输，不含任何起草/agent逻辑。** 跟 `wechat_bridge.mjs` 是同一个
设计思路，靠两个文件跟外部agent(这个项目里就是Claude Code对话本身)通信；但底层实现完全不同，
见下面"跟wechat_bridge.mjs的关键差异"。

## 跟 wechat_bridge.mjs 的关键差异

1. **没有独立bot身份**：小红书私信没有类似WeChat ClawBot那种官方"机器人频道"产品，这里驱动的
   是你自己的真实小红书账号——发出去的消息就是"你"发的，不是一个隔离开的机器人身份。自动化的
   是你的真实账号，这一点跟WeChat那边本质不同，风险也不同。
2. **不走接口，走DOM**：小红书的私信接口(会话列表/聊天记录)需要页面内部专有的签名逻辑，直接
   拿URL重放会被拒(实测调用 `/api/im/web/v3/chats` 之类的接口直接返回 `result:-7`)。所以这里
   放弃了接口方案，改成 Playwright 读真实渲染出来的DOM + 模拟点击/打字，跟人用浏览器操作是一个
   原理，不去逆向签名算法——这样风险也更接近"正常使用浏览器"而不是"重放接口"。
3. **复用 MediaCrawler 的登录会话**：直接指向 `../MediaCrawler/browser_data/xhs_user_data_dir`
   这个已经登录过的 Chromium profile，不用重新扫码。代价是**这个脚本运行时不能跟 MediaCrawler
   抓取同时跑**——同一份 profile 文件会被 Chromium 锁住，两边抢着用会冲突。以后如果私信这边用
   得频繁，值得花时间单独扫码搞一份独立 profile，两边互不影响。

## 启动

```bash
cd ~/IdeaProjects/scooter-dm-helper
node xhs_dm_bridge.mjs
```

会打开一个真实浏览器窗口(不是无头模式，方便你随时盯着/介入，尤其是发送这个动作)。
脚本要**一直挂着跑**才能收发消息。

### 安全阀：DRY_RUN

```bash
XHS_DM_DRY_RUN=1 node xhs_dm_bridge.mjs
```

开启后，发送步骤只会把文字打进对话框，**不会真的按回车发出去**——第一次真正验证"发送到底是不是
按回车触发的"，建议先开这个开关，自己在旁边看着确认一次，确认没问题了再关掉正常跑。

## 对外接口：两个 jsonl 文件

### `xhs_inbox.jsonl` —— 本脚本写，agent 读

```json
{"id": "550e8400-...", "ts": 1755230000000, "platform": "xhs", "from_user_id": "<conv_id>", "from_name": "卖家昵称", "text": "还在的，170可以"}
```

| 字段 | 说明 |
|---|---|
| `id` | 这条消息唯一ID，回复时用这个 |
| `from_user_id` | 小红书会话的 `conv_id`(DOM里的 `data-conv-id`，不是对方的用户主页ID) |
| `platform` | 固定是 `"xhs"`，跟 `wechat_bridge.mjs` 的 `inbox.jsonl` 区分开，两边不共用文件 |

**只会推送启动之后新收到的消息**——第一次运行会先扫一遍全部会话建立"已读到第几条"的基线，
不会把历史消息全部倒进inbox里。对方分享笔记/卡片消息进来会转成 `[分享了笔记]标题` 这种占位文字。

**已知限制**：只处理一对一私聊(`data-conv-kind !== "group"` 的会话)，群聊跳过不处理。

### `xhs_outbox.jsonl` —— agent 写，本脚本读

```json
{"reply_to": "550e8400-...", "text": "在的，多伦多哪边方便见面？"}
```

跟 `wechat_bridge.mjs` 一样，`reply_to` 对不上就跳过并打日志，不会重试也不会报错给agent。

## 轮询频率

- 会话列表：每15秒扫一次，靠"预览文字有没有变"决定要不要点进去细看，没变就跳过——不用每次
  都把全部会话点一遍，也更不像高频轮询的机器人行为。
- outbox：每2秒检查一次有没有新行。

## 已知限制

- 只支持文本消息(自己发的/对方发的都一样)，其他富媒体消息类型没有针对性解析，会被归为
  `[无法解析的消息类型]`。
- 单会话单账号，不支持多小红书账号。
- 没有做 jsonl 文件的自动清理/轮转，长期跑需要自己定期归档。
- "新消息"判断靠"数DOM里对方气泡的条数变化"，不是真正的消息ID对比——理论上如果对方一次性
  撤回又发了等量消息，可能漏判，这是个人项目量级的实现，没做消息可靠性保证。
